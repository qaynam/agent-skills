# Self-Documenting Code

## 原則

コードが第一のドキュメント。コメントと API ドキュメントは、隣接する構文の
言い換えではなく、**コードとは異なる抽象度の情報**を足すために存在する。

- **実装コメント（`//`）** → 理由・制約・不変条件・ワークアラウンド
- **API ドキュメント（`/** */`）** → 利用者から見た意味・契約・副作用
- **コミットメッセージ / PR** → 変更の歴史（コード内には書かない）

コメントにはコードと同期させ続ける保守コストがある。そのコストを上回る
情報価値が読み手（利用者またはメンテナー）にある場合に書く。密度はコード量
ではなく非自明さに比例させる。整理されたコードの大半はコメント 0 で成立し、
本当に難しい箇所には段落を書いてよい。

## ワークフロー

1. **観察** — 対象ファイルの既存コメントの言語・密度・スタイルを見る。
   ドキュメント作業が主題なら、lint / doc 生成設定（`eslint.config.*`,
   `tsdoc.json`, `typedoc.json`, `api-extractor.json`）と CONTRIBUTING も確認。
2. **分類** — 3 軸で分類してから書く：
   - ファイル種別：`.ts`/`.tsx` か、JSDoc を型付けに使う `.js` か、公開ライブラリか
   - API 境界:外部利用者向けの公開 API か、内部実装か（`export` ≠ 公開 API）
   - 寿命：恒久的な挙動か、削除条件を持つ一時コードか
3. **構造優先** — 「何を」のコメントを書きたくなったら、先に命名・型・
   assertion・関数抽出を検討する → `references/refactor-first.md`
4. **執筆** — JSDoc/TSDoc を書く前に `references/documentation-guide.md`、
   実質的な実装コメントを書く前に `references/inline-comments.md` を読む。
5. **検証** — 変更したコードの近傍のドキュメントが依然として真か確認し、
   下の最終チェックを実行する。

## 優先順位

1. リポジトリ固有の規約・既存コードの慣習
2. 設定済みの lint / doc 生成ツールの要求
3. フレームワーク・ライブラリの規約
4. このスキルのデフォルト
5. Google Style 等の一般ガイド

## MUST（違反禁止）

- 依頼・差分・会話を実況するコメントを書かない
  （「〇〇対応のため追加」「ご要望により変更」「新規ヘルパー関数」）。
  変更の文脈はコミットメッセージと PR に書く。
- 意味情報を足さずに隣接する構文を言い換えない。
- `.ts`/`.tsx` では TypeScript の型注釈を JSDoc に重複させない
  （`@param {Type}` 禁止）。ただしこのルールを、JSDoc を型付けに使う
  `.js`/`.jsx` に適用しない。
- 関数のドキュメントに偶発的な呼び出し元を書かない（契約を書く）。
  例外は呼び出し元自体が契約であるフレームワーク上の取り決めのみ。
- 自分の変更で不正確になった近傍のコメント・doc は更新または削除する。
  腐ったコメントは無コメントより悪い。
- リファクタリング中に、有用な既存コメントを剥がさない。
- 公開 API の重要な副作用・例外・null 等の意味を隠さない。
- コメントアウトされたコード、コード内の変更履歴・署名・日付を残さない。
- コメントとコードが矛盾していたら、推測で進めず、どちらが正しいか
  解決してから進む。

## 耐久性テスト（コメント・doc を書く前に）

1. 現在の会話や差分を知らない読み手にも意味が通じるか。
2. コードの挙動が変わらない限り真であり続けるか。変更に追随できない
   場所へ事実を複製していないか。
3. 一時的な処理なら、削除条件と（安定した追跡先があれば）参照を書いたか。
4. その事実は型・assertion・テストで検証できないか。できるならそちらを優先。
5. 置き場所は、記述対象のコードと一緒に変更されやすい場所か。

## SHOULD

- コメントの前に命名・構造の改善を検討する。
- 公開契約は利用者に最も近い宣言に集約する。
- 一時コードには削除条件を添える。
- `@example` は最小かつ動く形にする。

## MAY

- 順序が重要な一本道のアルゴリズムに短いフェーズコメントを書く。
- 名前とシグネチャで自明な公開関数の doc を省略する。
- 非自明な引数だけに `@param` を書く（部分的なリストで構わない）。

## 最終チェック（差分に対して実行）

1. 実況コメント・言い換えコメントが 0 か。
2. doc に呼び出し元・`{型}`・TS と重複する情報がないか（`.ts` の場合）。
3. 触ったコードの近傍のコメントがすべてまだ真か。
4. 実行可能な検証があるなら回す：型チェック、JSDoc/TSDoc 系 lint、
   doc 生成、`@example` がコンパイル可能か。
