# 実装コメント（`//`）ガイド

実質的な実装コメントを書く前に読む。`/** */` は API 利用者向け、
`//` は実装メンテナー向け。

## 書く正当な理由

1. **What ではなく Why** — 非自明な判断の根拠。
2. **コード上は恣意的に見えるビジネスルール** — 出典を添える：
   `// 1万円未満は非課税（国税庁ガイドライン XX）`
3. **ワークアラウンド** — 下の「一時コード」参照。
4. **不変条件・事前条件** — ただし下の「検証の優先順位」を先に適用。
5. **警告・落とし穴**：`// 順序が重要：auth ミドルウェアを先に実行すること`
6. **非イディオマティックなコード** — 「間違って見える」書き方が正しい理由。
   誰かが善意で「直して」しまうのを防ぐ。
7. **非自明な性能上の選択**：`// Set で検索：ここでは n が 10 万を超えうる`
8. **コピー／改変したアルゴリズムの出典**（リンク）。
9. **正規表現・ビット演算・数学** — 下の「正規表現」参照。
10. **`TODO`** — 後で行動できる文脈がある場合のみ。追跡先があれば
    `// TODO(#123): ...`。漠然とした `// TODO: 改善する` は書かない。
11. **フェーズコメント** — 順序が重要な一本道のアルゴリズムで、関数抽出が
    かえって流れを壊す場合（`references/refactor-first.md` の基準参照）：

    ```ts
    // Phase 1: 到達可能なノードを収集
    ...
    // Phase 2: 強連結成分を縮約
    ...
    ```

## 不変条件：検証の優先順位

コメントは事実を「主張」するだけで検証しない。可能な限り実行可能な形へ：

1. **型で表現**：`function mergeSortedItems(items: readonly Item[])` /
   `SortedList<Item>` 型を作る
2. **assertion で検証**：`assert(isSortedByCreatedAt(items));`
3. **テストで固定**
4. **名前で示す**：`sortedItems`
5. それでも表現できない前提だけをコメントに書く

ローカルな文脈に結びついたコメントは正当である（耐久性テストの通り、
問題は「移動すると無効になること」ではなく「変更に追随できない場所への
事実の複製」）：

```ts
// ✅ 直前の stableSort により createdAt 昇順になっている
for (const item of items) { ... }
```

ただしこれも assertion にできるなら、そちらが上位。

## 一時コード（ワークアラウンド・互換処理・移行コード）

一時的な挙動では**時間軸が契約の一部**になる。実況禁止ルールの例外では
なく、「現在コードが存在する理由と削除条件」を書くこと。以下を含める：

- 何が壊れるか／どの条件で発生するか
- なぜ通常の実装にしていないか
- **削除条件**（バージョン、日付、外部の修正）
- 安定した追跡先が**あれば**添える（issue、チケット）。なければ条件だけで
  よい — リンクは必須ではない

```ts
// Safari 18.2 では ResizeObserver が同一フレーム内に二度通知される。
// 18.4 未満のサポート終了後に debounce を削除する。WEB-482 参照。
```

```ts
// Legacy v1 payload は、4.8 未満のモバイルクライアントがサポート対象
// バージョンのしきい値を下回るまで受け付ける。削除は APP-1842 で追跡。
```

## 正規表現

「平易な言葉への翻訳」だけではパターン変更に追随できない。書くべきは
**サポート範囲の契約**：

```ts
// `{{name}}` 形式のプレースホルダーだけを対象とする。
// ネストした波括弧やエスケープ構文はサポートしない。
const placeholderPattern = /\{\{[^{}]+\}\}/;
```

加えて有効な手段：名前付き部分式への分解、受理する文字列・拒否する
文字列の例、仕様や出典へのリンク、**何を完全には検証しないか**の明記。

## 書いてはならないもの

- 次の行を言い換えるコメント（`count++` の上の `// カウンターをインクリメント`）
- 依頼・差分・会話の実況（「〇〇対応のため追加」「ご要望により変更」）。
  恒久的な理由があるなら出来事ではなく理由を書く：
  `// エラー送出時にバッチ全体を中断させるため for...of を使う（#482）`
- 閉じ括弧ラベル（`} // end if`）
- コメントアウトされたコード — 削除する。git が覚えている
- コード内の変更履歴・署名・日付（`// 2026-07-29 〇〇が修正`）
- ユーザーやレビュアーに宛てた文（「なお、〜も行いました」）

## 既存コメントの扱い

- 変更で嘘になった近傍のコメントの更新・削除は、変更の一部であり任意ではない。
- リファクタリングでは、耐久性テストを生き残るコメントを剥がさず、記述対象の
  コードと一緒に移動させる。
- コメントの言語・密度・スタイルはファイルの慣習に合わせる（日本語コード
  ベースなら `@param user - ブロック対象のユーザー` のように日本語で）。
