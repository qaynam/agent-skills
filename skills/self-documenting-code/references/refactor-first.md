# コメントの前に構造を検討する

「何を」のコメントを書きたくなったときに読む。多くの場合、意味は名前・型・
構造に押し込めてコメント自体を不要にできる。ただし各手には適用条件があり、
機械的に適用すると可読性を壊す。

## 手のリスト

| 書きたくなったコメント | 検討する手 |
| --- | --- |
| 真偽値の式の説明（`// 編集可能かチェック`） | 説明変数 `const canEdit = ...` または述語関数 `canEdit(user)` |
| 長い関数のセクション見出し | 関数抽出（下の基準を満たす場合のみ） |
| マジックナンバーの説明 | 名前付き定数（下の基準を満たす場合のみ） |
| 巧妙なワンライナーの解説 | 退屈な複数行バージョンで書く |
| 呼び出し側での引数の意味説明（`f(user, true)`） | オプションオブジェクト／名前付き引数 |
| 意外な挙動の注記（`// 見つからなければ null`） | 型で表現（`User \| null`）、または `findUser` に改名 |
| 事前条件の主張 | 型 → assertion → テスト → 名前（inline-comments.md の優先順位） |

## 関数抽出の基準

抽出するのは以下を満たす場合：

- 独立した意味のある操作として**命名できる**（名前をひねり出す必要がない）
- 入出力が自然に定義できる（一時変数を大量に引数化しない）
- 単独でテストまたは再利用する価値がある、**または**抽出により
  データフローが明確になる

逆に、順序が重要な一本道のアルゴリズムで、抽出すると制御フローの見通しや
局所性を失うなら、**短いフェーズコメントのほうが正しい**。実装上だけ存在する
不自然な抽象を作らないこと。

## 定数化の基準

名前付き定数にするのは：

- 複数箇所で共有する値
- 意味・変更理由がある値（ビジネスルール、仕様値 — 出典も添える）
- 単位が曖昧な値
- 設定として扱う値

局所的な実装値まで定数化すると、定義へジャンプしないと値が分からなくなる。
一箇所でしか使わない実装上の値は、単位を添えたインラインでよい：

```ts
await sleep(100 /* ms */);
```

## 判断の軸

リファクタリングはコメント回避の手段であって目的ではない。抽出・定数化・
改名がコードを読みやすくするならやる。コメントを消すためだけに構造を
複雑にするなら、コメントを書くほうが正しい。本来のタスクを差し置いて
リファクタリングを優先しない — 気づいた改善が変更範囲外なら、提案に
とどめる。
