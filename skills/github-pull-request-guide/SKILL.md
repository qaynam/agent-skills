# GitHub Pull Request Guide

## 目的

レビューしやすく、変更の目的、実装内容、検証結果、残っている作業を正確に伝えるPRを作成する。

PR本文の作成だけで終わらせず、スコープの整理、差分の精査、コードコメントの整理、検証、関連タスクの記録、PR作成後の確認まで行う。

## 情報の優先順位

判断が衝突する場合は、次の順に従う。

1. タスク指示者が今回の依頼で明示した指示
2. リポジトリ内の `CONTRIBUTING.md`、`.github/PULL_REQUEST_TEMPLATE.md`、開発ガイド、CIルール
3. このスキル

上位のルールを優先し、下位のルールを黙って無視しない。レビューに影響する差異がある場合は、PR本文の注意事項に記載する。

## 作業フロー

次の順序で進める。

1. タスクとリポジトリのルールを確認する
2. 複数タスクの分割方法と依存関係を決める
3. ブランチ、コミット、差分をすべて精査する
4. 一時コメントやセッションメモを整理する
5. 必要なテスト、静的検査、手動確認を行う
6. 実際の差分と検証結果からPRタイトルと本文を作る
7. PRを作成または更新する
8. PR上の表示、リンク、base/head、差分を再確認する

ユーザーがPR本文の下書きだけを依頼した場合は、手順6まで行い、PRの作成やコメント投稿は行わない。

## 1. タスクと事実を確認する

PR本文を会話中の記憶だけで作らず、必ず実際のタスク、ブランチ、コミット、差分を確認する。

確認する情報:

- PRの対象となるタスクと受け入れ条件
- target/baseブランチと現在のheadブランチ
- リポジトリ固有のPRテンプレートと開発ルール
- baseからheadまでの全コミットと全差分
- 関連するIssue、仕様、議論、先行PR、後続PR
- 変更に伴うリリース、移行、設定変更、運用作業

## 2. 複数タスクを分割する

一つのPRは、レビュー担当者が一つの問いとして理解できる、まとまりのある変更にする。

複数タスクを依頼された場合は、最初に依存関係を整理し、次の基準で判断する。

### 別々のPRにする

次のいずれかに当てはまる場合は、原則としてPRを分ける。

- 変更目的が独立している
- 片方だけでも安全にマージ、リリース、または取り消しできる
- レビュー観点や検証方法が大きく異なる
- 無関係なリファクタリング、整形、依存関係更新が混在している
- 分けたほうが差分とリスクを明確に説明できる

### 一つのPRにまとめる

次のいずれかに当てはまる場合は、一つのPRにまとめる。

- 変更を分けると各PRが動作しない、または検証できない
- データ移行と利用側の変更など、同時にマージする必要がある
- 一つの不変条件を成立させるために複数箇所の変更が不可分である
- 分割によって一時的に壊れた状態が生じる

### stacked PRにする

タスク間に順序付きの依存関係があり、各段階を独立してレビューできる場合は stacked PR を優先する。

例:

```text
main <- feature/base-change       # PR 1
feature/base-change <- feature/ui # PR 2
feature/ui <- feature/cleanup     # PR 3
```

stacked PRでは次を守る。

- 最初のPRだけを通常のtargetブランチに向ける
- 後続PRのbaseを直前のPRのheadブランチにする
- 各PR本文に依存するPR、後続PR、推奨マージ順を記載する
- 各PRの差分を、そのPRのbaseに対してレビュー可能な大きさに保つ
- 先行PRのマージ後に、後続PRのbase変更またはrebaseを行う
- 先行PRが未マージでも、そのPR単体で説明と検証ができる状態にする

複数の分割案が同程度に妥当で、選択によってレビュー、リリース、または実装方針が変わる場合だけ、作業開始前にタスク指示者へ確認する。明らかな依存関係がある場合は、分割案と理由を示したうえで進める。

## 3. PR前に差分を精査する

PR本文を書く前に、要約だけでなくbaseからheadまでの差分全体を読む。

最低限、次を確認する。

- 意図した変更だけが含まれている
- 別タスクの変更やローカル実験が混ざっていない
- デバッグ出力、一時フラグ、使われていないコード、コメントアウトしたコードが残っていない
- 自動生成ファイルやlockfileの変更が意図どおりである
- 認証情報、トークン、個人情報、内部URLなどが含まれていない
- 変更したAPI、型、設定、データ形式の利用側が追従している
- エラー処理、後方互換性、移行、ロールバックへの影響を見落としていない
- PR本文で説明する内容が実際の差分と一致している

差分に無関係な変更を見つけた場合は、原則として別コミットまたは別PRへ分離する。分離できない理由がある場合は、PR本文で理由を説明する。

## 4. コードコメントとセッションメモを整理する

リポジトリに `/references/self-documenting-code.md` が存在する場合は、先に読み、その内容を正とする。存在しない場合、または今回必要な判断が書かれていない場合は、[references/comment-cleanup.md](references/comment-cleanup.md) を読む。

コメントを次のように分類する。

### コードに残すコメント

- 実装から読み取れない「なぜ」を説明する
- 仕様上の制約、不変条件、安全上の理由を説明する
- 外部仕様、既知の不具合、互換性のための回避策を説明する
- 将来の変更時に壊してはいけない前提を説明する

### 削除または書き直すコメント

- コードをそのまま日本語で読み上げている
- 作業途中の考え、会話、セッションの進捗を記録している
- 「とりあえず」「あとで直す」など、根拠や条件がない
- 完了済みのTODOや古い仕様を説明している
- 実装と一致していない
- AIとの会話、内部の推論過程、個人的なメモが含まれている

### PRコメントへ移す

削除対象のコメントに、レビューで共有すべき判断、懸念、未解決事項が含まれている場合は、削除前に内容を短く整理し、PRコメントとして残す準備をする。

- 生のセッションメモをそのまま転載しない
- 内部の推論過程、認証情報、個人情報、不要な会話を含めない
- レビューに必要な結論、制約、トレードオフだけを残す
- `[memo]`、`[imo]`、`[question]` のいずれかを先頭に付ける
- 可能なら該当する変更行にインラインコメントする
- 該当行が削除されている場合は、最も近い変更行かPR全体のコメントに、ファイル名と対象シンボルを添えて投稿する

タグの使い分けと文例は [references/comment-cleanup.md](references/comment-cleanup.md) に従う。

PRへの書き込み権限がない場合、またはPRがまだ存在しない場合は、ファイル、行またはシンボル、タグ、本文を含む「投稿予定コメント」として保持する。PR作成後、権限と依頼範囲を確認して投稿する。

## 5. テストと動作確認を行う

リポジトリのドキュメント、package scripts、CI設定から正式な検証コマンドを特定する。変更に関連する最小限の確認だけでなく、リポジトリで必須とされている検査も行う。

変更内容に応じて次を検討する。

- unit test、integration test、end-to-end test
- lint、format、typecheck
- build、生成物の差分
- 手動操作による正常系と代表的な異常系
- migration、互換性、ロールバック
- パフォーマンス、アクセシビリティ、セキュリティ

結果は、実際に行ったことだけを記録する。

- コマンドを実行した場合は、コマンドと結果を記載する
- 手動確認では、前提、操作、期待結果、実際の結果が分かるようにする
- テストを追加した場合は、何を担保し、何を担保していないかを記載する
- 実行できなかった確認は「未実施」とし、理由と影響を記載する
- 「確認済み」「問題なし」だけで済ませない
- 実行していないテストや存在しない結果を作らない

未実施の必須確認があり、まだマージ可能でない場合はDraft PRとして作成するか、PR作成前に解消する。マージ前に必要な作業を「マージ後TODO」へ先送りしない。

## 6. PRタイトルと本文を書く

リポジトリに既存の命名規則がある場合は従う。規則がない場合、PRタイトルは変更によって何が可能になるか、または何が直るかを簡潔に表す。

避けるタイトル:

- `修正`
- `対応`
- `いろいろ変更`
- 実装手段だけを並べたタイトル
- 実際の差分より広すぎるタイトル

PR本文を書く前に [references/pr-body-template.md](references/pr-body-template.md) を読み、必要なセクションだけを使用する。

本文の基本順序:

1. `概要`: 何のためのPRか、何が問題だったか、どの方針で直したか
2. `変更内容`: レビューすべき主要な変更
3. `動作確認`: 実行した確認と結果
4. 必要に応じて、テスト、設計判断、依存PR、注意事項、マージ後TODO

### 書き方

- PR本文だけを読んでも背景と変更内容が理解できるようにする
- 最初に結論と主要な変更を書き、細部は後に置く
- 一文に一つの論点を書く
- 因果、対比、補足が必要な箇所では接続詞を使う
- 並列する変更、確認手順、TODOには箇条書きを使う
- ファイル一覧を変更内容の代わりにしない
- コミットメッセージをそのまま貼り付けない
- 同じ内容を複数セクションで繰り返さない
- 空のセクションや「特になし」だけのセクションは削除する
- 議論していない代替案や存在しない合意を作らない

### 条件付きで記載する内容

**テスト**

テストを追加または変更した場合、何を担保したか、どの境界やケースを未確認かを書く。

**設計判断・代替案**

複数の実装案を比較した場合、採用案、見送った案、判断理由、残るトレードオフを書く。自明な変更に形式的な代替案を捏造しない。

**依存PR**

stacked PRや先行変更への依存がある場合、依存先、後続PR、マージ順を書く。

**注意事項**

レビュー、リリース、設定、データ移行、互換性に関する注意がある場合だけ書く。

**マージ後TODO**

マージ後でなければ実行できない作業だけをチェックボックスで書く。可能なら担当者、実行条件、関連タスクを付ける。

## 7. PRを作成または更新する

PR作成時に次を確認する。

- baseとheadが意図どおりである
- タイトルと本文が実際の差分を表している
- stacked PRの依存関係とマージ順が書かれている
- 未完了の必須作業がある場合はDraftになっている
- リポジトリの規則に従ってラベル、担当者、レビュアーを設定している

コードから移した投稿予定コメントがある場合は、PR作成後に該当箇所へ投稿する。単なる作業ログやレビューに不要なメモは投稿しない。

ユーザーが明示的にPR作成を依頼していない場合は、PRを作成せず、タイトル、本文、投稿予定コメントを提示する。

## 8. PR作成後に再確認する

作成または更新したPRを開き、次を確認する。

- Markdownが崩れていない
- Issue、依存PRのリンクが正しい
- baseとheadが正しい
- 想定外のコミットやファイルが含まれていない
- 動作確認と未実施事項が正確である
- 投稿した `[memo]`、`[imo]`、`[question]` コメントが適切な場所にある
- 機密情報や内部の推論メモが公開されていない

完了報告では、PR URL、検証結果、未解決事項、stacked PRの場合は順序を簡潔に示す。

## 完了条件

次をすべて満たした場合にPR準備完了とする。

- 一つのレビュー可能な目的にスコープが整理されている
- 複数タスクの分割またはstacked PRの判断が説明できる
- baseからheadまでの全差分を精査している
- 一時コメント、デバッグコード、無関係な変更を整理している
- 必要な文脈だけを適切なPRコメントへ移している
- 実施した検証と未実施の検証を正確に記載している
- 必要な設計判断、依存関係、注意事項、マージ後TODOが記載されている
- PR作成後にbase、head、差分、リンク、表示を再確認している

## 禁止事項

- タスクURL、テスト結果、議論、合意、仕様を推測で作らない
- 実際の差分にない変更をPR本文へ書かない
- 生のセッションメモ、内部の推論過程、機密情報をコードやPRへ残さない
- 無関係な変更を説明なしで同じPRに混ぜない
- 必須のマージ前作業をマージ後TODOへ移さない
- すべてのセクションを機械的に出力しない
- 「問題ありません」「よしなに対応しました」のような検証不能な表現で済ませない
