セクションごとの基準

概要

最初の1〜3段落で次を伝える。

何のためのPRか

何が問題だったか

どの方針で解決したか

問題が自明な小規模変更では、背景を長く書かない。変更内容の羅列から始めず、目的を最初に置く。

変更内容

ファイル名ではなく、レビュー担当者が確認すべき振る舞い、構造、制約を書く。

悪い例:

- `foo.ts` を変更
- `bar.ts` を変更

良い例:

- APIレスポンスの判定を共通関数へ集約し、画面ごとの条件差をなくした
- 不正なレスポンスを受けた場合は、空表示ではなく既存のエラーUIを表示するようにした

動作確認

結果を再現できる粒度で書く。実行していない確認は書かない。

悪い例:

- 一通り確認しました

良い例:

- `pnpm test src/parser.test.ts`
  - 既存12件と追加3件がすべて成功
- 開発環境で空のレスポンスを返し、エラーUIへ遷移することを確認

関連タスク

必ず独立したセクションにする。

テスト

テストコードを追加または変更した場合に使用する。「何をテストしたか」だけでなく、そのテストからは保証できないことも必要に応じて書く。

設計判断・代替案

実際に比較や議論があった場合だけ使用する。自明な変更で形式的な代替案を作らない。

注意事項

リリース手順、feature flag、migration、互換性、既知の制約など、レビューまたは運用に影響する情報だけを書く。

マージ後TODO

マージ後にしかできない作業だけを書く。テスト不足、未修正の不具合、必須レビューなど、マージ前に終えるべき作業を入れない。

短いPRの例

## 概要

検索結果が0件のときにローディング表示が残り続ける問題を修正します。取得完了と結果の有無を別々に判定し、0件の場合は空状態を表示するようにしました。

## 変更内容

- ローディング終了条件をレスポンス件数から取得状態へ変更
- 0件時の空状態表示を追加
- 0件と通信失敗を区別するテストを追加

## 動作確認

- `pnpm test src/search/search-state.test.ts`
  - 追加2件を含む全14件が成功
- 開発環境で0件のレスポンスを返し、空状態へ切り替わることを確認

## 関連タスク

- [検索結果0件時の表示を修正](https://example.invalid/task-url)

## テスト

- 担保したこと: 0件、1件以上、通信失敗の表示分岐
- 担保していないこと: 実ブラウザでのスクリーンリーダー読み上げ
