# コードコメントの整理とPRコメントへの移し替え

## 目的

コードには長期的に必要な説明だけを残し、レビュー時だけ必要な判断材料、意見、質問はPRコメントへ移す。作業セッションのログや内部の推論過程は、コードにもPRにも残さない。

## コメントを残す判断基準

次の質問に一つ以上「はい」と答えられるコメントだけを、コードに残す候補とする。

*   実装を読んでも分からない理由を説明しているか
*   仕様、互換性、安全性、性能上の制約を説明しているか
*   将来の変更で壊しやすい不変条件を説明しているか
*   外部システムや既知の不具合に対する回避策を説明しているか
*   コメントがないと、自然に見える変更が誤りになる理由を説明しているか

残す場合も、現在の実装と一致する短い文章へ書き直す。

## 削除するコメント

次のコメントは原則として削除する。

*   コードの処理をそのまま読み上げるコメント
*   作業順、進捗、会話内容を記録したコメント
*   完了済みのTODO
*   根拠のない「暫定」「とりあえず」「念のため」
*   実装と食い違う古い説明
*   デバッグ用のメモ
*   AIとの会話、プロンプト、内部の推論過程

## PRコメントへ移す手順

1.  コメントを削除する前に、ファイル、対象シンボル、関連する変更行を記録する
2.  元のコメントから、レビューに必要な結論、制約、懸念、質問だけを抽出する
3.  生の文章をコピーせず、1つの論点につき1つの短いコメントへ書き直す
4.  `[memo]`、`[imo]`、`[question]` のいずれかを付ける
5.  コードから不要なコメントを削除し、必要ならコード自体を読みやすく書き直す
6.  PR作成後、該当する変更行へ投稿する
7.  該当行がない場合は、最も近い変更行かPR全体のコメントへ、ファイル名と対象シンボルを添えて投稿する

PRコメントへの書き込みができない場合は、次の形式で投稿予定コメントを出力する。

```markdown
- 場所: `src/example.ts` の `parseResult`
- タグ: `[question]`
- 本文: 空文字列も未入力として扱う仕様でよいでしょうか。現在の実装では `null` と `undefined` だけを未入力として扱っています。
```

## タグの使い分け

### `[memo]`

レビュー担当者が知っておくと理解しやすい、確定済みの背景や制約に使う。回答や変更を必須にしない。

```markdown
[memo] この分岐は旧APIとの互換期間中だけ必要です。互換期間終了後の削除は別タスクで管理しています。
```

### `[imo]`

採用した判断に対する意見やトレードオフを共有し、レビューを求める場合に使う。事実と意見を混同しない。

```markdown
[imo] ここでは共通化よりも分岐を明示したほうが、2つのエラー処理の差を追いやすいと判断しました。
```

### `[question]`

仕様、設計、命名、境界条件など、回答が必要な未解決事項に使う。質問と、その回答が変更へ与える影響を書く。

```markdown
[question] 期限切れデータも一覧へ残す仕様でしょうか。除外する場合は、この絞り込み条件をAPI側へ移します。
```

## 投稿しない内容

次の内容は、タグを付けてもPRへ投稿しない。

* 内部の逐語的な推論や思考過程
* 認証情報、個人情報、非公開URL
* 単なる作業日誌
* レビューに影響しない独り言
* すでにコードとPR本文から明確に分かる説明
* 相手に求める行動が不明な曖昧な質問

## 変換例

コード内の不要なコメント:

```ts
// さっき話した通り、いったんここで弾く。あとでAPI側に移すかもしれない
if (!isSupported(value)) return null;
```

コードに残す必要がある制約がある場合:

```ts
// Reject unsupported values here because the legacy API returns HTTP 200 for them.
if (!isSupported(value)) return null;
```

レビューで実装場所を相談したい場合は、コードコメントを削除し、次のPRコメントへ移す。

```markdown
[question] 未対応値の判定を今回はクライアント側へ置いています。API側へ移す場合は旧クライアントへの影響があるため、互換期間終了後の別変更に分ける想定でよいでしょうか。
```
